# 优化方案实施与验收状态

## 性能优化候选（未发布）

第一批在独立分支实施，仅供测试，尚未同步公开主线：

- 历史采集复用 SQLite 连接，每轮把成功读取的两个来源合并为一个事务；只在超出容量时执行淘汰扫描。保留每秒采样、精确保留期限、10 万条上限、只读查询及 DELETE 日志模式。
- 代理 API 共享不可变 JSON 与预计算 ETag；并发冷读和主动刷新合并抓取，失败保留最近有效快照，核心暂不可用时限制重试。
- 代理页面复用节点名称解析、区域选项、节点卡片、延迟曲线及订阅用量元素；折叠组延迟处理成员信息。数据变化仍更新，排序、筛选、焦点和操作权限继续回归。
- 基线与候选用同样数据验证。历史合成负载为 1 万条已有记录、两个来源各 500 条、30 轮；测试磁盘中位耗时约 95.5 → 50.1 ms，累计写入约 61.3 → 38.1 MB，最终记录摘要一致。浏览器 60 组、1000 候选、120 张可见主组卡片的刷新中位耗时约 104.7 → 46.3 ms，主组每轮子节点变更 726 → 0。数值是指定合成场景，不代表真实转发吞吐提升。
- 复验：`scripts/benchmark-observer.py --baseline <旧版 history_store.py> [--directory <测试磁盘目录>]`；`scripts/verify-proxies-fixture.cjs <前端构建目录> --performance --evidence=<证据目录>`。临时数据库仅含合成记录；真实环境证据留在 Git 之外。
- 完整候选 `0.2.3-perf.1` 从提交 `d3e15ea` 构建，独立目录的新装、升级保留配置和历史记录验证通过；实际安装模块的 30 项相关测试通过。原生测试实例升级后配置、节点选择、核心及历史记录保留，45 个实际 HTTP 页面文件与安装包一致。小快照的 40 次条件请求均返回 304，接口延迟前后接近；没有据此宣称真实吞吐提升。尚未推送或公开发布。

本轮先减少已确认的重复工作。连接聚合锁、TCP/UDP 参数和整体转发吞吐继续依负载剖析决定，不凭接口或页面耗时推断。

同一测试分支的侧栏改进：入口统一简写，按“网络 / 观测 / 管理”分组并缩进；桌面支持收起到图标栏且记住状态，手机保持完整抽屉，底部外观和退出按钮固定。桌面、短窗口、320px 手机、亮暗主题与设置草稿、诊断任务导航保护回归通过，尚未公开发布。

## 已实施：观测快照兼容（测试通过，未发布）

优先级 P1，先于历史采集降频、事务合并和缓存优化。2026-11-07 核对：正式 v0.2.3 的观测接口会把内部 `/connections` 返回的 `connections: null` 拒绝为 `INVALID_CORE_RESPONSE`；历史采集器遍历同一空值时会跳过本轮 Mihomo 写入，异常被外层处理忽略。这影响观测正确性，不能通过前端空状态或降频掩盖。`null` 的产生方尚未直接核对，不能据此断言来自 Mihomo 原生接口。

- 在观测 API 与历史采集器中一致处理合法快照对象的空值：`null` 与 `[]` 表示本次无记录；`false`、`0`、空字符串、对象及含非法元素的列表仍应拒绝，网络和认证失败不转换为空快照。空快照不代表没有流量、完整历史或转发成功，采样年龄未知时保留未知语义。
- 采集失败增加限频、脱敏的诊断记录，避免静默跳过；不输出凭据或连接内容。
- API 与采集器共用严格校验，`yaml`/`suburl` 均覆盖“空闲 → 有连接 → 空闲”；身份变化和失败仍按秒等待，避免立即重试空转。Linux Python 全量回归 361 项通过，前端单测 36 项通过，Rust 1060 项通过、5 项原有用例忽略；浏览器覆盖焦点保留、曲线更新、筛选、隐藏规则及桌面/手机。
- 完整候选包与已安装文件已核对，真实空闲快照返回 HTTP 200、空列表、`complete_history: false` 及未知采样时间；未认证请求仍返回 401。正式 v0.2.3 尚未包含修正，公开主线与正式发行包须在测试获准后一起更新，不能用测试实例补丁代替发布。
- 5 项上游原有忽略用例涉及真实公网 DNS、TLS 指纹和 Cloudflare 临时隧道；隔离回归不启用公网。DNS 两项保留为专项公网冒烟，精确 Chrome 指纹属于可选兼容检查。Debian 明确禁用 CF，隧道两项不属于本版本必要验收；它们主要输出诊断与评分，也不能将退出成功作为严格业务验收。当前保留并通过了“即使配置残留 token，Debian 也不启用 CF”的回归。

## 已完成：Mihomo 自动选型与统一发行包

默认按系统实际支持的 CPU 等级选择 Linux amd64-v3、v2 或 v1。Debian 的 glibc loader 同时检测 CPU、操作系统与虚拟化环境；没有明确检测结果时使用 v1。允许管理员指定较低等级；未确认支持的高等级拒绝安装。选型改变只保存设置，点击安装 / 更新才替换同版本核心。

官方资产优先匹配明确的 v1/v2/v3 文件名；v1 允许回退到旧 compatible 名称。旧名称可能从未来 Release 移除，因此不能继续固定为 compatible。只接受官方稳定版、准确资产名、官方下载地址和 SHA256；缺少资产或摘要时停止安装，不猜测下载链接或跳过校验。

更新判断使用数字版本比较：未安装可安装，只有更高稳定版属于自动升级；相同版本的 CPU 型号变化独立提示，由管理员手动安装。已安装版本较新不自动降级；无法识别的现有版本保留并提示。手动离线上传允许同版本换型，完全相同的二进制不重启。候选必须实际运行版本检查、通过配置预检和启动验收，失败沿用原核心。

验证范围：CPU 等级和检测失败、型号设置保存、官方资产匹配、缓存重新选型、数字版本比较、同版本换型、离线重复安装、损坏下载拒绝和启动失败回退；网页覆盖桌面/手机、草稿保护和状态说明。完整包从同一提交构建 Rust、Python 和最新前端，并校验源码、产物与安装清单。补做干净安装、升级保留配置以及失败回退，避免完整包落后于独立 UI 更新。

官方依据：

- [Mihomo 文件说明](https://wiki.metacubex.one/startup/faq/)
- [Mihomo 构建矩阵](https://github.com/MetaCubeX/mihomo/blob/Meta/.github/workflows/build.yml)
- [Go amd64 最低要求](https://go.dev/wiki/MinimumRequirements#amd64)

自动选择策略由本项目根据官方等级定义实现；官方没有保证更高等级在所有负载下都更快。
